# ADR-0001：実行単位の計測・比較と保存方式

状態：提案。2026-10-12。

## 背景

ISUCONでは継続監視より、短いベンチマークの結果を比較し、次の改善を決めることが重要。既存のALP、pt-query-digest、Linuxツールを利用しており、人とAIの両方が根拠を参照できるようにしたい。

[pprotein](https://github.com/kaz/pprotein)はGo向けで、pprof/fgprof/alp/slpとの連携を掲げている。Go固有のProfile機構はそのまま使えないが、異なる計測結果を一つの調査環境へ集める方向性を参考にする。

## 課題

計測基盤が競技サーバーのCPU、メモリ、I/Oを奪う。実行結果・コード・設定・計測条件の対応が曖昧だと比較できない。リアルタイム基盤を当日に構築すると分析より構築に時間を費やす。

## 選択肢

| 選択肢 | 利点 | 問題 |
|---|---|---|
| OTel + ClickHouse + Grafana | SQLでTrace・Log・集計を横断でき、複数人で同時分析しやすい | 常駐DB、スキーマ、権限、TTL、挿入・merge負荷の運用が必要 |
| OTel + Jaeger/Tempo + Prometheus | Trace UIと時系列分析に既存機能を使える | データ横断の問い合わせが複数APIに分かれ、Log保存も別途必要 |
| 構造化ファイル + DuckDB | 常駐DB不要、結果を持ち運べる、SQLで比較できる | ファイル確定・変換が必要、標準のTrace UIはない |
| 既存CLIのみ | 最短で導入できる | 実行間比較と根拠の横断参照を人手で行う |
| pproteinの拡張 | 既存の集約・表示機能を利用できる可能性 | Node Profile形式や非Go対象への拡張可否はソース監査・PoCが必要 |

## 結論

MVPは既存CLIと構造化ファイルを採用し、分析端末でDuckDBを使う。実行ID、manifest、比較レポートを中心にする。OTelは収集手段として追加し、保存方式への依存をアプリに持たせない。

ClickHouse、Grafana、常設MCP、専用Web UIはMVPの必須要件にしない。pproteinを丸ごと移植する判断も保留し、Node.js向け収集と既存pproteinの再利用を小さなPoCで比較する。

## 影響

初期はリアルタイム性とTrace UIの利便性を一部犠牲にする。OTLPファイルの読み込み・正規化は実装が必要で、DuckDBがOTLPをそのまま理解するとは仮定しない。標準UIが必要なら診断時だけJaeger等を併設する。

保存原本は変更せず、分析ビューを再生成できるようにする。全バックエンドに対応する抽象レイヤーは作らない。

## 再検討条件

外部保存先が競技規約上許可され、専用分析マシンを確保できること。その上で、複数人の同時利用、数秒単位の速報、蓄積量、DuckDBのクエリ時間が実際に問題になったらClickHouseを評価する。データ量だけで自動的に採用しない。
