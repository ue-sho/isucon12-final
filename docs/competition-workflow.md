# 競技当日の進め方

最初の40分を目安に、基準スコアがあり、計測でき、3人が改善に着手できる状態を作ります。40分は目安です。立ち上げに時間がかかっても、基準を取る前に性能変更を重ねないようにします。

操作・設定は [isutools README](../isutools/README.md)、当日の担当と実施状況は [Issue #2](https://github.com/ue-sho/isucon15/issues/2) で管理します。競技ルール・採点方法・変更可能範囲は、当日の公式情報を確認してください。

## 記録する場所

| 場所 | 記録すること |
|---|---|
| Issue #2 | 当日の担当、立ち上げ・終了前の実施チェック、基準計測へのリンク、残作業 |
| 改善ごとのIssue | 観測した問題、改善仮説、対象コード・API・SQL、期待する効果、担当、検証結果、採否と次の一手 |
| PR | 実装差分、変更理由、検証内容。関連する改善Issueをリンク |
| docs | 繰り返し使う手順、確認できた仕様・構成、引き継ぎに必要な知識、保存した調査・計測ファイル |

改善の着手前に、改善Issueへ「観測した問題・仮説・対象・期待する効果」を短く書きます。調査中の議論や失敗した案、計測結果、採否も同じIssueに追記します。事実・仮説・検証結果は区別してください。新規Issueには[改善・調査テンプレート](../.github/ISSUE_TEMPLATE/improvement.md)を使えます。

同じ内容をIssueとdocsへ二重に書く必要はありません。繰り返し参照する仕様や構成が分かったときにdocsへ整理し、Issueからリンクします。大きなログや計測ファイルは内容を確認して保存し、Issueには場所と要点を記録します。

## 担当と排他

| 担当 | 主な役割 |
|---|---|
| A：インフラ・計測・統合 | セットアップ、デプロイ・ベンチの実行管理、基準値と計測結果の共有 |
| B：アプリ・仕様 | 採点・制約・ユーザーフローの把握、APIとアプリコードの調査・改善 |
| C：DB・データ | スキーマ・初期化・データ量の把握、SQL・インデックスの調査・改善 |

担当名と代行方法はIssue #2に記入します。Aに作業が集中したらB/Cが実行を代行し、実行者と対象コミットを共有します。SQLを呼ぶコードとインデックスを同時に変更するときはB/Cで担当範囲を調整します。

`task deploy` / `task bench` は全ホストで同じデプロイロックを使います。`task bench` は完了までロックを保持し、終了不明時も残します。ポータルからの手動ベンチ・直接のDB変更・初期化・重い解析はロック対象外なので、Aに宣言して重複を防ぎます。終了不明のベンチはポータルで終了を確認してから `task unlock` します。

## 立ち上げ

最初に全員で、ポータル・競技マニュアル・接続情報・ルール・変更可能範囲・再起動と最終判定の条件を確認します。使用言語、担当、共有先、ベンチ・デプロイ・DB変更の宣言場所を決めます。

### A：インフラ・計測・統合

1. 全員のSSH設定・agent転送・Task・Pythonを確認します。bootstrap / benchの実行者はAnsibleも準備します。
2. `isutools/config.env` の接続先・リポジトリ・アプリ・DB・ビルド・pproteinホストを実環境に合わせてcommit・pushします。
3. サーバーの初期状態を変える前に `task inspect` を実行します。`docs/inventory/<UTC取得時刻>/` の内容を確認してcommit・pushします。収集範囲は[構成調査](initial-inventory.md)を参照してください。
4. 言語切替・計測設定・性能変更の前に、ポータルから無変更ベンチを実行し、成功可否・スコア・エラー・時刻を記録します。
5. 使用言語と有効にするアプリサービスを決めます。サービスの有効化・無効化は手動で行います。
6. mainで `task bootstrap` を実行します。初期コード・ホスト別設定と計測設定を別コミットで保存します。初期SHAは `isutools/initial-state.json`、元のnginx / MySQL設定は各ホストの `/home/isucon/backup/etc/` で確認します。DBデータのバックアップは対象外です。Gitに含める範囲は[初期状態の参照](../isutools/README.md#初期状態の参照)を参照してください。
7. `/initialize` の先頭に `triggerPproteinCollect()` をawaitせず組み込み、ブランチをcommit・pushして `task deploy` します。
8. `task status` で反映SHAとサービス状態を確認します。`task pprotein` でUIを開き、alpのURL集約設定を問題に合わせます。
9. 計測設定ありの基準ベンチを取り、httplog / slowlog / Node profileを収集・解析できることを確認します。言語切替や計測設定の前後で基準を区別します。
10. ポータルAPIの認証・対象ID・実動作を確認できたら `task bench` を使います。未確認なら `task deploy` と手動ベンチをAの管理下で行います。設定は[ベンチ実行](benchmark.md)を参照してください。
11. CPU・メモリ・ディスクI/O・プロセス別負荷の取得方法と保存先を決めます。現状は専用Taskがありません。
12. SHA・設定/構成・スコア・エラー・alp/slp・リソース情報を同じ試行として保存・共有します。Discordは任意通知であり、一括ローカル保存は未実装なので手動で残します。
13. 正常コミットを指すpush済みブランチへ `task deploy BRANCH=<ブランチ>` で戻せることを確認し、切り戻し先を共有します。SHA直接指定・アプリのみ/設定のみのデプロイは未対応です。
14. 確認した構成・操作方法はdocsに残し、未取得項目・残作業はIssue #2に記録します。

重い解析はベンチ終了後に行います。デプロイ時にアクセスログ・slow logを切り詰めるため、前の計測の解析・保存が済むまで次のデプロイをしないでください。

### B：アプリ・仕様

マニュアル・API定義・採点方法を読み、Web画面を操作して主要なユーザーフローを確認します。主要APIからDB・外部サービスまでの処理を追い、認証・整合性・キャッシュ・非同期化の制約を確認します。

確認できた仕様や構成はdocsへ整理します。Aの計測結果と照合して、時間の大きいAPIのコードを調べ、改善候補を個別のIssueへ記録します。優先順位と次に試すことを共有してください。

### C：DB・データ

`task inspect` の結果を基に、DBの種類・バージョン・接続先・主要設定と未取得項目を確認します。テーブル・インデックス・件数・容量、initializeで戻るものと戻らないものを把握します。件数は原則概算、インデックス詳細は別途確認が必要です。正確な件数が必要なら `task inspect -- s1 --database <DB名> --exact-counts` をベンチ外で使います。

スロークエリ上位を実行回数・総時間・走査行数で整理し、実行計画と呼び出し元コードを確認します。SQL・インデックスの改善と初期化への反映方法を改善Issueに記録し、Bと変更範囲・依存関係を共有します。実行を伴うSQL解析や大量集計はAと調整します。

### 40分時点の共有

基準ベンチの成功可否・スコア・エラー・SHAを共有し、リソース・API・SQLのどこが詰まっているか確認します。各担当が最初に試す改善Issueを1つ選び、担当・優先度・状態をIssue #2からたどれるようにします。未完了の立ち上げ作業には担当と次の確認時点を付けます。

## 改善サイクル

1. 改善Issueへ、観測した問題・仮説・対象コード/API/SQL・期待する効果を記入します。未検証の仮説を事実として扱わないようにします。
2. 関連する改善Issueを確認し、担当・依存・競合を調整します。比較できる単位で変更し、PRからIssueをリンクします。
3. レビュー・統合後、Aと実行順を調整して同条件でベンチを取ります。反映は `task deploy BRANCH=<ブランチ>`、反映とベンチは `task bench BRANCH=<ブランチ>` です。省略時は現在ブランチのpush済みコミットを全ホストへ反映します。
4. 改善Issueに前後の条件・計測結果・採否を記録します。失敗した案と理由、次の一手も同じIssueへ追記します。
5. ボトルネックの変化に合わせて担当と優先順位を見直します。再利用する知識はdocsへ整理し、Issueからリンクします。

計測記録は、時刻／実行者／コミットSHA／設定・構成／変更内容／成功可否／スコア／エラー内訳／解析結果／採否を含めます。計測ファイルやPR・Actionsのログはリンクでひも付けます。

サーバーを分割したらホスト別設定を変更し、`task pprotein:targets -- split` で計測対象を広げます。

## 終了前

残り60分を目安に開始します。実施チェックはIssue #2で付けます。停止・再起動の対象は `HOSTS` と `PPROTEIN_HOST` で確認します。

1. Aが正常コミットと切り戻し先を共有し、大きな構成変更の締切を決めます。
2. Bが最終コードの仕様適合とmainへの統合を確認します。Cは初期化後もスキーマ・インデックス・必要データを再現できることを確認します。
3. Aがホスト別のnginx / MySQL設定で不要なアクセスログ・slow logを止め、アプリのdrop-inから `NODE_OPTIONS` を外し、`PPROTEIN_ENABLED=0` にします。
4. 設定をcommit・pushし、`task deploy BRANCH=main` で全ホストへ反映します。
5. 全ホストの `pprotein-agent.service` とpproteinホストの `pprotein.service` を手動で `sudo systemctl disable --now <サービス名>` にします。デプロイは有効化・無効化を変更しません。
6. `task status` で反映SHA・アプリ状態・`agent=inactive`・不要なロックがないことを確認します。pprotein本体の停止とアクセスログ・slow logが増えていないことも確認します。
7. ルールに沿ってサーバーを再起動し、アプリ・nginx・DBが必要な構成で自動起動し、計測サービスは停止したままであることを再確認します。
8. 初期化を含む最終ベンチを実行します。API確認済みなら `task bench BRANCH=main`、未確認ならAの管理下で手動実行し、成功・スコア・エラーを保存します。
9. ベンチ後の `task status` と記録を照合し、稼働SHA・設定・接続先が一致し、必要な提出操作が完了していることを全員で確認します。

参考：[Yasuo Team's Isucon Best Practices](https://gist.github.com/minhquang4334/26e86a84731164581ed25d3fc7fe5211)。初動・競技中・終了前に分ける構成を参考にしています。
